# DEVLOG：这支片子是怎么做出来的

一份工程日志。**重点是犯过的错**——因为改掉的判断比写对的代码值钱。

时间跨度：2026-09-30 深夜到 2026-10-01 上午。成品在**国庆节当天早上**发布。
从看到参考项目开源地址，到成片发出，**7 小时**。

## 0. 起点：逆向一支别人的片子

一切从一条 B 站链接开始。目标是搞清楚一支代码渲染的 PV 是怎么做的。

**第一个发现**：仓库地址不在视频简介里，在 **UP 的置顶评论**里。
B站 `x/v2/reply/wbi/main`（`mode=3`）的 `data.top_replies` 匿名可得。
——找「视频附带的仓库」，先看置顶评论，别在简介里翻。

**逆向出的工作流（五段）**：

```
check（工具/字体/歌曲 sha256）
  → lyrics（本机合成歌词，只存时间不存文字，逐行 sha256）
  → dancer（用立绘生成同格式替身帧）
  → pages（每帧一张 HTML → 无头浏览器截图）
  → render（PIL 逐帧 → ffmpeg；无损母版 → 转码）
```

**三个内核**（后面本片完整继承）：

1. 每一帧都是歌曲时间 `t` 的**纯函数**；
2. 界面用真前端的 CSS 拼静态 HTML，**动画被 pause 并 pin 到 `t*1000 % duration`**（保证可复现）；
3. 换图层靠**内存里 monkey patch**，不改生产文件。

### 复现的三个实证结论

1. 抽 15 帧与源码常数逐条对照，**全部吻合**——连 0:05 那个蓝像素就是某个 `SEED` 都对得上。
2. 同一个 `body(20.0)` 调两次**逐字相同** ⇒ 纯函数成立。
3. **仓库不能开箱即跑**：某个模块在**模块级**就要词级时间轴，没有自备歌词连 `import` 都失败。

第 3 条很重要——它是一份**刻意的设计**：干净地剥离版权内容，代价是开箱可跑性。
本片把这个取舍**照搬**了（见 [NOTICE.md](../NOTICE.md)）。

### 踩的坑

- **不要 `python xxx.py | head`**：管道一断 python 抛 `BrokenPipeError`，
  **后面写盘的部分不执行**，白跑一轮。
- **asar 格式**：header JSON 后有 padding，数据区起点 = `(16 + header_size + 3) & ~3`。
  用 `16 + header_size` 差 2 字节 ⇒ 提取出的 CSS 大小一样但 sha256 完全不同，
  **差点误判成「文件不同」**。

## 1. 移植：换歌第一件事是重新标定时钟

拿到任务：以另一首歌为基底做同类 MV，**尽量不动原稿的技术路线和呈现形式**。

**第一件事不是写代码，是标定 BPM。** 原稿的教训是「不许先跑起来看看」。

踩的陷阱：钢琴曲的 onset 自相关给了 **110.0 BPM**（附点）与 **73.34**（其 2/3）两个强候选——
**倍频歧义**。换一个更硬的锚：**歌词句间隔**，实测中位数 **3.3300 s**，稳定得惊人。

令「一句 = 4 拍」⇒ **BPM = 72.072**。

**反向验证**：按该网格给 onset 包络打分，`72.07` / `36.04` / `144.14`（同一网格的 1×/½×/2×）
**得分几乎相同**——这正是「网格选对了」的指纹。若选错，倍频之间会明显拉开。

### ★ 两个本机大坑

**小文件 IO 是渲染瓶颈。** 7922 张 PNG 写盘只有 **~1.1 MB/s**，
12 分钟毫无进度，**而且并行比串行还慢**。单帧渲染只要 84 ms，墙钟时间几乎全花在文件系统上。

> 解法：worker 把帧**流式喂进各自的 ffmpeg stdin**（`-f rawvideo -pixel_format rgb24 -i -`），
> 出无损分片再 `-c:v copy` 拼接。全片降到 **293.8 s**。

**多进程 libx264 OOM。** `x264 [error]: malloc of size 13213312 failed`——
当时可用内存只剩 **2.0 GB / 16.8 GB**。分片编码器换 `utvideo`（无损 RGB、内存占用极小），
并发降到 3。

> **并发数要按内存定，不要按核数。** 24 核默认给到 22 worker = 44 进程，直接 `MemoryError`。

## 2. 「这真的是本地做的？」——取证

被问了一句「天呐这个真的是你在本地做的而不是下载的成片」。不解释，取证。

### ★ 最强单一判据

**「现场复算 + 逐像素比对」。** 用源码**当场**再渲一遍同一时刻的静帧，与成片对应帧比：

> 若 **MAE 恰好 0、最大差恰好 0、100% 像素逐位相同**，一次测量同时证明两件事：
> ① 成片由本机源码生成（下载件不可能与现算结果逐像素重合）；② 渲染是**确定性**的。

三个辅助判据：

1. **容器指纹**：平台件自带 `Packed by Bilibili XCoder` 且 852×480/yuv420p；
   渲染母带是 `gbrp` / High 4:4:4 Predictive / 24 Mbps——**平台一律不提供这种格式**。
2. **反向对照**：同 t 与参考片比只有 30–42% 像素相同，且那部分全是纯黑/平坦区 ⇒ 不同源。
3. **素材链时间戳**：参考仓库解压时间 < 本片中间产物生成时间。

## 4. ★ 坑一：分段缓存让构建撒谎（连中两次）

改了 5 个镜头，`render` 报「7922 帧全部 cached，0.6s」，`verify` 却 **MAE 12.7**——
**主片还是上一版。**

- 第一次修：按源码摘要做失效 → **条件写反**，首次盖戳那轮仍然全 cached（同样失败）。
- 第二次修：缓存失效要删 50+ 分段 → **被 safe-delete 护栏拦下**（第三次失败）。
- **最终修法：根本不删。把缓存这一层整个去掉**，每次全量渲染（约 3.5 min），
  ffmpeg `-y` 原地覆写。

> **教训：校验管线本身会说谎时，先修管线再修画面。**
> MAE 0 是验收线，量不了就等于没量。

## 5. ★ 坑二：豆腐——而且判据本身也是错的

**症状**：某处标题行**自己用等宽字体手画**，绕过了按码点选字体的逻辑，中文变成一排空框。

**修法要成类，不成点。** 只修肉眼看到的那两处是不够的。写 `tools/tofu_audit.py`：
包一层文字绘制函数，全片逐 0.5 s 渲染，凡「等宽字面 + 非 ASCII」一律记账。
一次抓出 **8 处肉眼没发现的**。

**然后是判据本身出错。** 后来加了整屏代数式（`· ³ π μ √ − ² ρ →`）之后，
旧判据把这些**正常的数学符号全报成豆腐**，一次 14 处误报。

> 改成**真比对字形**：该面 `getmask(ch)` 为空，或等于它自己的 `.notdef`。
> 复跑 **0 处**。

**顺带纠正一个更细的判断**：`needs_cjk` 判 `>0x7F`，**不能拿它判整行**——
Consolas 自带一批数学符号，整行推到中文字体反而难看。整行判断要判 `>0x2E7F`。

> **MAE 0 只证明「可复现」，不证明「可读」——豆腐完美复现。**

## 6. ★★ 方法论一：整片均值看不到局部改动

给片子加了几处新内容，第一版验收报「**4.55% vs 4.53%，无变化**」。

**是假象。** 13 个均匀采样点**全部落在五处改动之间**，一个都没命中。

改用**同帧 A/B**（同 shot 名 = 同种子，只换元素 ⇒ 差就是改动本身）后：

```
五处局部均值   墨量 3.17%  →  4.38%   (+38%)
               峰值 178.3  →  211.6   (+19%)
单镜最猛 shot_noise: 墨量 3.64 → 6.78%   峰值 167 → 250
```

> **教训：验收局部改动必须用同帧 A/B。** 全片均匀采样会完全跳过它。

**并诚实记下代价**：亮部 `lum>120` 反而 **0.73% → 0.50%**（−0.23%），
集中在某一镜——那是画风适配换来的，不许说成全面提升。

## 7. ★★ 方法论二：lint 全绿，观众看到的是 52 秒什么都没发生

被指「3:20–4:07 部分重复素材太多」。诊断结果：

**同一份九条数据讲了四遍，两个器件各用两遍。**

而 `check_variety()` 判据是**相邻对**——这四镜**每一对都不同** ⇒ **0 issue，全绿**。

> **lint 报 0 的地方，观众看到的是 52 秒什么都没发生。**

**修法一：把判据的窗口加宽。** 重复的定义是
「**同一份数据 × 同一个器件**在窗口内的出现次数」，窗口要开到**整个段落**。
检测器应统计 `(数据源, 器件)` 直方图，任何一项 >1 就报警。

**修法二：不是换器件，是换问题。** 同一份九条数据可以被问四次而都成立：
`who（名册）→ how fast（累计计数）→ how long（1970–2026 跨度）→ where（就位在画面里）`。
四个器件互不相同，且**只有第一个在枚举**。

**重复感的另一半成因是「时间上没有事发生」**：进度参数 `u*1.7+0.15`
让 9 行在**第 5 秒就全亮**，之后 8 秒放着已完成的清单。
给揭示函数加 `pace` 参数（本段用 0.95 = 整镜都在填），让揭示铺满镜头长度。

### 顺带发现：右栏「几乎没什么用」

右侧边框栏是事件滚动条。**可用宽度只有 62 px**，循环里

```python
while len(txt) > 4 and textlength > avail:
    txt = txt[:-1]
```

把**每条中文事件截成 4 个字**。整片就是「boot --miss / propellant l / 东方红 太阳」。

**不报错、不 lint、接触表上看不出来。**

改成**结构拆解**：六件部件纵向堆叠（天线 / 壳体 / 银锌电池 / 短波发射机 / 乐音装置 / 观测裙），
按章节**点亮当前讲到的那一件**，底部显示该件读数。

> **横着读是章节表，竖着读是卫星本体。** 两种读法都不吃宽度。

### 本轮最深的教训

这两处**都不是 bug**——**都能跑、都 lint 全绿、都 MAE 0.000**。

> **流水线的所有客观检查都对，片子仍然难看。**
> 「所有检查都通过」不等于「片子对」。

所以验收也必须换仪器：lint → 加宽窗口的重复直方图；全片均值 → 同帧 A/B。

## 8. ★★ 发现：墨量靠「面」不靠「线」

想给片子加空气动力学公式。先做**离线标定**（不动工程），量四种画法：

| 版本 | 墨量% | 高光% | 峰值 |
|---|---|---|---|
| 本片（改动前） | 4.53 | **0.00** | 155.8 |
| 参考片 | 10.41 | 0.51 | 242.0 |
| v1 只塞内容（**全是线**） | **1.51** | 0.00 | 143.7 |
| v2 线 + 白热 | 1.54 | 0.32 | 238.3 |
| v3 **面积图**（同一条线改成面） | **7.51** | 0.00 | 143.7 |
| v4 面积 + 白热 | **7.54** | 0.32 | **238.3** |

**两个结论**：

1. **把线换成面：1.51% → 7.51%（5 倍）。** 参考片的 10.41% 是**面**堆的，
   不是更多日志行。⇒ 若「塞公式」仍画成线条，墨量**比原来还低**。
2. **白热层只管亮度，不管墨量**（1.51→1.54）：峰值 143.7 → 238.3、高光 0 → 0.32%。

> **两个杠杆正交：**「仪表化（面）」管墨量，「白热层」管亮度，**缺一不可**。

### 顺带发现：全片结构性没有高光

参考片高光 `lum>190` 占 0.51%，本片 **0.00%**。
根因：**调色板最亮色 `(255,176,0)` 亮度上限只有 143.7，而后期只减不加。**

所以本片一度「一级原因不是细节少，是**没有高光**」。
解法是 `tk.hot(level)` 白热层，**每帧只准一个元素用**。

## 10. 4K：能做，但不是改个数字（最后决定不做）

被问能不能渲 4K。诊断结论：**分辨率在 6 个文件里各硬编码了一遍**，
所有坐标都是 720p 空间的**裸 px**；绘图对象直接暴露底层 `ImageDraw`，
绕开它的直绘点约 **103 处**；后期同样是 px 单位（扫描线**每 3 px 一条**、模糊半径写死 4）。

**实测（不是估计）**：

| 项 | 720p | 4K（S=3） | 倍数 |
|---|---|---|---|
| 单帧渲染 | 84.8 ms | — | — |
| 后期模糊 | 19.4 ms | **186.5 ms** | **×9.6** |
| 200 行文字 | 34.0 ms | 80.5 ms | ×2.4 |
| 母版体积 | 3.83 GB | 约 34 GB | ×9 |

先做了最省事的方案（从**无损母版**上采样，不是从 720p 交付片二次压缩），结果有个意外收获：

> **4K 成片即使降回 720p 看，也比原 720p 版更接近源帧**（MAE 1.970 → 1.701）。
> 因为 4K 的 yuv420p 色度平面是 1920×1080，而 720p 路径只有 640×360，**色度子采样损失更小**。

**最后决定不做。** 理由：源本身只携带 720p 的信息量，
**调高码率不增加真实信息量**——4K 在这里只是一个标签。

### 若真要做，四条工程要点

1. **用 `S` 参数化，默认 `S=1`** ⇒ 现有 720p 行为**逐位不变**，4K 是**新增档**而非替换 ⇒ 零回归风险。
2. 缩放只注入**三个咽喉点**：`Ctx.d`（代理 ImageDraw，坐标 ×S）、字体 size ×S、后期参数 ×S。
3. ⚠️ **最大的坑**：临时精灵内部用**裸 `ImageDraw`** 画在 720p 尺度上，**代理拦不到**，
   必须单独按 S 生成，否则贴上去会变小。
4. ★★ **可判定的验收**：把 4K 帧**降采样回 720p**，与现有 720p 帧比 MAE。
   缩放开销全对 → 只剩抗锯齿差异；**任何一处漏乘 S，MAE 会在局部炸开**。

⚠️ 还有一条**审美**警告：扫描线是这套 CRT 语言的一部分，720p 下每 3 px 一条。
4K 若照搬 3 px 周期 ⇒ 变成 720 条，**观感完全不同**。必须按比例放到 9 px 周期。

## 11. 一条时间戳的教训

统计发布里程碑时，本鱼把 GitHub 的 `created_at`（仓库建立）当成了「开源时刻」，
算出「距开源 24 小时」，与实际情况对不上。

被纠正：**锚点不是仓库创建时间，而是 UP 在置顶评论里给出仓库地址的时刻。**
改用之后：**+7 小时**，正是「国庆节当天早上」。

**最难堪的一点**：证据当时就在记录里——
仓库的 `updated_at` 比那条置顶评论晚约 1 分钟，而工作目录名里的时间戳距置顶**只有几十秒**。
两条都在案，却被判成「语义不确定」放过去了。

> **不是没数据，是没把数据当回事。**

顺带修了另一个错：某视频的发布时间被记成 `20:57`，实为 `12:57`——
沙箱时区本来就是 `+0800`，`fromtimestamp()` **已经是本地时间**，又加了一次 8 小时。

## 12. 账：这个工作区花了多少消耗

被问「整个工作区大概一共花了多少 token」。答案**不能只说一个数**：

| 口径 | 数值 |
|---|---|
| **流经总量**（每次请求的 input+output 累加） | 168.37 M |
| —— 其中缓存重读 | 165.76 M（**99.1%**） |
| 真正的新输入 | 1.56 M |
| 输出 | 1.05 M |
| **真正新增合计** | **2.61 M**（流经 : 新增 ≈ **64 : 1**） |

> 不是「花了 1.68 亿」——是**同一份上下文被重发了 1028 次，而其中 99.1% 命中了缓存**。
> 这是 agent loop 的固有形态：每调一次工具就得把整段历史重发一次。
> **缓存命中率才是最该盯的健康指标。**

**两个口径陷阱**（跨项目通用）：

- 每条记录带**两份完全相同**的用量数据（snake/camel 各一份）——按块统计会**翻倍**，要按行去重。
- 口径与 Anthropic **相反**：这里的 `input_tokens` **包含**缓存命中，
  `cache_read_input_tokens` 是它的**子集**而非累加项。写成 `input + cache_read + output` 会把缓存读算两遍。

## 13. 最后：这支片子做对了什么

回头看，整支片子最值钱的一点，是**「让东方红一号自己的记录回答」**这条纪律。

一个具体例子。片中有一组问句（「浮游一般的人生 / 要如何度过」），
第一版用影片自己的隐喻作答（雾、日出、蜉蝣）——被否了：

> 「应该让东方红一号本身的故事来回答，而不是我们替观众回答。」

于是改版：**只列她自己的记录**，每行都能在事实层查到——
点火 / 运载 / 入轨 · 播送 / 周期 / 静默日 · 2009 重测轨 / 2026 仍在轨。

另一处。片尾有一句「今天仍在轨道上」。它旁边刚放的是一张面积图：

> 半长轴衰减 **0.884 m/圈**，39 年 **179,934 圈**。

**她说「仍在轨道上」，脚注是「每天真掉 0.884 米」。标题与正文互证。**

这就是这支片子跟「励志片」的区别：**它不是靠修辞说服你，是靠记录。**

## 14. 发布工程：把一个工作区变成能给别人跑的仓库

片子做完之后的事，最容易漏记——因为它不在「创作」里。但这一段的坑**最贵**：
它们全都属于「本机跑得通，别人跑不通」这一类，而且**不会在你自己机器上暴露**。

### 14.1 可移植性改造：八处

把工程从 `_sr/`（本工作区）搬到独立仓库，要断开所有「只有这台机器成立」的假设：

| # | 原状 | 现状 |
|---|---|---|
| 1 | `tuikit.py` 里 `MV` / `EXPR_DIR` / `EXPRS` 指向参考项目的立绘 `whale-*.webp` | **全删**（本片零外部图像素材） |
| 2 | 三个图元函数按*表情名*查表：`conv_maps(expr, crop, ...)` | 改为**接收图像** `conv_maps(src, ...)` |
| 3 | 零调用残留 `halfblock_lum()` / `halfblock()` | 删除 |
| 4 | ffmpeg 路径硬编码 `SR.parent/_tools/ffmpeg/...` | `PV_FFMPEG` → `shutil.which("ffmpeg")` → 兜底 |
| 5 | 音频路径硬编码 | `PV_SONG` → `audio/song.mp3` |
| 6 | 字体路径硬编码 Consolas | 全部 `PV_F_*` 可覆盖 + 系统默认 |
| 7 | 歌词直接读本工作区 | `PV_LINES` + **sha256 逐行校验** |
| 8 | 无 LRC 入口 | 新增 `tools/lrc.py`（.lrc → `lines.local.json`） |

> **判断标准**：把这台机器上不存在的两样东西（歌、歌词）拿掉，
> 剩下的还能不能 `import`？不能就说明还有硬依赖没断。

### 14.2 版权边界的机制，而不是口号

「不含歌词」不能靠人记，要靠**结构**：

- 仓库只存 `song.timeline.json`：50 行的**起止时间 + 每行 sha256**；
- 用户自备歌词 → `pvclock.py` **逐行比对 sha256**，对不上**直接退出**；
- 于是**不可能**出现「拿 A 版歌词配 B 版时间」的静默错位。

代价也已写明：没有歌词文件时**连 `import` 都过不去**（词级时间轴在模块级被需要）。
**这是刻意选的**：干净剥离版权 > 开箱即跑。

### 14.3 ★ 一个许可证被识别失败的原因

GitHub 起初把仓库的许可判成 **`NOASSERTION / Other`**，而不是 MIT。

原因不在正文，在**正文之后**：为了写清「本许可证只覆盖代码」，在标准 MIT 全文后面
追加了一段范围说明。**许可识别器遇到非标准内容就放弃识别**，整份判为「其他」。

**修法**：`LICENSE` 只留 MIT 标准正文，范围说明搬到 `NOTICE.md`（它本来就是干这个的）。
改完立刻识别为 `MIT`。

> **教训：许可证文件是给机器读的，NOTICE 才是给人读的。** 别在许可证里加解释。

### 14.4 ★★ git 凭据助手是「累加」的

沙箱里 `git push` 第一次直接失败：`could not read Username，terminal prompts disabled`——
非交互环境，弹不出凭据窗口。解法是用能**读系统凭据库**的 `wincred`：

```bash
git -c credential.helper=wincred push -u origin main
```

但把它写进配置后，**裸 `git push` 反而挂死**。原因：

> **`credential.helper` 是列表，不是单值。局部设置会「附加」在全局之后，不会覆盖。**

全局本来就有两条（`helper-selector` + `git-credential-manager.exe`）。
局部再加一条 `wincred`，实际顺序是 GCM 先跑 → 它照样尝试交互 → 卡住。

**正确写法是先清空再设**：

```bash
git config --local --add credential.helper ""        # 清掉继承来的
git config --local --add credential.helper wincred   # 只留这一条
```

改完裸 `git push` 秒回 `Everything up-to-date`。

### 14.5 推送前的三道关

版权件一旦进了历史，**删掉文件也删不掉历史**。所以顺序必须是「先验拦截，再暂存」：

1. **造诱饵**：放几个假文件（`audio/song.mp3`、`work/lines.local.json`、`work/*.lrc`），
   用 `git check-ignore -q` 逐个确认 `.gitignore` **真的**拦得住；
2. `git add -A`，然后 `git diff --cached --name-only` 看**实际**清单；
3. 再 `grep -Ei "\.mp3|\.wav|\.mp4|\.mkv|lines.*json|\.lrc$"` 复查暂存区，**空才提交**。

最终 52 个文件，无音频、无歌词、无成片。

### 14.6 元数据：两个小坑

- **topics 不能用 `PATCH /repos/{o}/{r}` 设置**，要单独 `PUT /repos/{o}/{r}/topics`，
  否则返回 200 但 `topics` 仍为空。
- **`.gitattributes` 要先于首次提交**：`* text=auto eol=lf` 能消掉 Windows 上的 CRLF 警告，
  否则每个 `git add` 都刷一屏 warning。

### 14.7 发布后的自检

```
git rev-parse HEAD origin/main     # 本地与远程必须同一个 commit
git ls-tree -r --name-only origin/main | wc -l   # 远程实际收到的文件数
```

再对仓库页发一次**匿名**请求（不带 token），确认 `HTTP 200` —— 别人能打开，才算真发布。
