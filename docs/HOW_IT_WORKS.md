# HOW_IT_WORKS：流水线是怎么运作的

一支 MV，没有剪辑软件，没有手工关键帧。**每一帧都是歌曲时间 t 的纯函数。**

## 为什么「纯函数」值得这么执着

```
frame(t) = 场景(t) → 搬运(t) → 主体(t) → chrome(t) → 后期(t)
```

输入只有一个浮点数，输出是一张图。看似朴素，但它买到四样东西：

1. **可逐像素验证。** 从源码当场重渲一帧，与母带比。若 MAE 恰为 0，
   一次测量同时证明了「画面由本机生成」与「渲染是确定性的」。
2. **可任意分块并行。** 第 3000 帧不需要第 2999 帧。分片渲染、分片编码、崩溃了只重跑那一片。
3. **修改可定位。** 想改某一格，就去改那个 t 对应的镜头声明，不用在时间轴上找。
4. **审片意见可 diff。** 分镜是表，改了什么一目了然。

**代价**：不能加时间轴拖影（会让帧依赖上一帧），也不适合做逐帧手绘式的观感微调。
本片接受这个代价——`trail=0`。

## 五层合成序

顺序是**固定**的，这是画面不散架的原因：

```
① 场景 scene      背景、底纹、该镜头的主要图形
② 搬运 carriers   跨镜头连续存在的物件（墨、轨道线）——它们是剪辑感的来源
③ 主体 subject    她（本片 = 卫星）
④ chrome          header 遥测行、右栏、底部歌词条 —— 每帧重画，永不参与变换
⑤ 后期 post       扫描线、暗角、网格遮罩、辉光
```

关键在 **④ chrome 不参与变换**：无论场景怎么晃、怎么缩、怎么切，
顶部那行遥测和底部那行歌词始终钉在原处。样式统一从这一条里长出来。

## 时钟层

`pv/pvclock.py`。它回答「t 这一刻在歌的哪里」：

- **BPM 与节拍**：72.072 / 一拍 0.8325 s，**一句唱词 = 4 拍**（标定过程见 [PORTING.md](PORTING.md)）
- **章节**：`00 PRE-FLIGHT` … `10 SUNRISE`，每章一个时间区间
- **吸附函数**：`snap(t, div)` 对齐网格、`pulse(t, decay)` 一拍一脉冲
- **歌词行**：`ROWS` / `rows_in(a, b)` / `lyric_at(t)`
- **两条弧线**：
  - `ui_gain(t)` ——「系统的颜色就是你。你走了，它就再也没能完全回来。」
    链路期最亮，电池耗尽时泄到 0.06，最后一个乐句再微弱回来。
  - `glow_arc(t)` —— 两段长间奏是全片两次「吸气」，辉光最亮。

## 分镜：三张表 + 一条 lint + 一条弧线

`pv/direction.py`。**一个 shot 只声明「语法 + 元素 + 参数」，不声明怎么画**：

```python
dict(name="shot_skirt", start=93.040, end=99.480, mode="split",
     els=[("skirt", dict())], her=dict(deploy=1.0, lit=0.75)),
```

- **表① `SHOTS`**：59 镜，覆盖 0.000–330.069 s，**无空隙**。
- **表② `CHOREO`**：转场表。默认 `reflow`（逐格字形切换，绝不条纹擦除）；
  每条都要写得出「为什么」。
- **表③ 动态规则**：`ui_gain(t)` / `glow_arc(t)` 把系统色与辉光写成时间的函数。

**一条 lint** `check.py`：`check_variety()`（相邻两镜不得语法与主元素同时相同）
+ `check_clock()`（每个边界必须落在唱词起音、章节边或器乐段内）。
两条都跑成 CI，不靠人眼。

> ⚠️ lint 全绿**不等于**片子对。`check_variety` 只看**相邻对**，
> 一个段落里反复用同一份数据它查不出来。这个教训见 [DEVLOG.md](DEVLOG.md)。

## 主体：她有多少张图

东方红一号自旋 **120 r/min = 2 r/s**，在 24 fps 下**每帧正好转过 30°**——
也就是 **12 个相位**。所以 `el_her` 只需要 12 张缓存相位图。
源码里有 `assert` 守住这个关系。这是「忠实」与「纯函数可控成本」正好重合的一处。

## 事实层

`pv/facts.py` 的原注释沿用原稿的纪律：**「One place to correct numbers.」**
所有上屏数字集中在这里，逐条注明出处。改动数字只改这一处。

口径写成四类，镜头里照此标注：

- `[事实]` — 可查证（CNSA / CAST / 科普中国 / Space-Track）
- `[推论]` — 由事实代入公认公式
- `[假定]` — 教科书典型值（`C_D=2.2`、`Isp=260 s`）
- `[推定]` — 从记录反解或外推

## 出片流水线（五段，每段独立可验）

```
① check    工具 / 字体 / 音频 / 时间轴 / lint / 形状 / 时钟
② 标定     几十张静帧覆盖全部场景类型（不许直接压满）
③ render   分片并行（worker 数**按内存定**，不按核数）
④ encode   无损母带 + 交付版 双轨
⑤ verify   现场复算 + 逐像素比对
```

**为什么中间不落 PNG**：7922 张小 PNG 只有约 1.1 MB/s，而单帧渲染只要 84 ms——
墙钟时间几乎全花在文件系统上，而且**并行比串行还慢**。
改成 worker 把帧**流式喂进各自的 ffmpeg stdin**，出无损分片再 `-c:v copy` 拼接，
全片 7922 帧降到 **293.8 s**。

## 后期

`engine.post()`：扫描线（每 3 px 一条）、暗角、半块字符网格遮罩、辉光。
**参数都是 px 单位**，与 720p 画布绑定——这是「分辨率写死在 6 个文件里」的根源，
扩到 4K 不是改个数字（诊断见 [DEVLOG.md](DEVLOG.md)）。

## 白热层：一个后加的纪律

调色板最亮色 `(255,176,0)` 亮度上限 143.7，而后期只减不加 ⇒ **全片结构性无高光**。
解法是 `tk.hot(level)`，把顶层琥珀推近白 `(247,247,247)`。

**每帧只准一个元素用。** 这条预算很紧：chrome 每帧都在，占掉白热就毁了纪律——
所以右栏的结构拆解只用 `amb(1.0)`，白热留给图表读数。

## 工具：怎么知道改对了

| 工具 | 回答什么问题 |
|---|---|
| `tools/cast` / `contact.py` | 这一段整体长什么样 |
| `tools/ab_loci.py` | **这次改动**让画面变了多少（同帧、同种子，只换元素，所以差就是改动本身） |
| `tools/tofu_audit.py` | 有没有字变成空框 |
| `tools/aero_mock.py` | 同一条数据的四种画法，各是多少墨量 |
| `contact_sheet.py` | 全片视觉索引 |
| `diag.py` | 哪一镜渲染最慢 |

> 最贵的一条方法论：**局部改动必须用同帧 A/B 验收，不能用全片均值。**
> 均匀采样点会全部落在改动**之外**，报「无变化」。见 [DEVLOG.md](DEVLOG.md)。
